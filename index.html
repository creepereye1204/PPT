Part 01 · 등장 배경

프롬프트 엔지니어링

모델에게 무엇을, 어떻게 요청할까

  • GPT-3 (2020) — 몇 개의 예시만 보여줘도 새 작업을 수행하는 few-shot 학습 발견
  • 모델 가중치를 바꾸지 않고 입력 텍스트만으로 동작을 제어할 수 있게 됨
  • Chain-of-Thought (2022) — “단계별로 생각해보자” 한 줄로 추론 성능 향상
  • ChatGPT (2022.11) 이후 누구나 쓰는 기술로 대중화

Part 01 · 장단점

프롬프트 엔지니어링

장점

  • 비용이 거의 없고 즉시 실험 가능
  • 파인튜닝·학습 데이터 불필요
  • 개발자가 아니어도 활용 가능
  • 빠른 프로토타이핑에 최적

단점

  • 문구 하나에 결과가 흔들림 (취약성)
  • 모델·버전이 바뀌면 다시 튜닝 필요
  • 모델이 모르는 최신·사내 지식은 못 넣음
  • 결과를 체계적으로 평가하기 어려움

Part 01 · 예시

역할 + 지시 + 예시 + 출력 형식

# 역할
당신은 쇼핑몰 고객 리뷰 분석가입니다.
# 지시
리뷰의 감정을 positive / negative / neutral 로 분류하세요.
# 예시 (few-shot)
리뷰: "배송이 빨라서 좋았어요" → positive
리뷰: "포장이 다 찢어져서 왔네요" → negative
# 출력 형식
리뷰: "{review}"
{"label": "...", "reason": "한 문장"}

역할·지시·예시·형식을 분리하면 결과가 안정적이고 수정하기 쉬워진다

Part 02 · 등장 배경

컨텍스트 엔지니어링

모델이 보는 정보를 설계하기

  • LLM 앱이 RAG·메모리·도구 결과·대화 기록을 함께 다루게 됨
  • “어떻게 묻느냐”보다 “무엇을 보여주느냐”가 성능을 좌우
  • 컨텍스트 창은 커졌지만(100K~1M 토큰) 길수록 중간 정보를 놓치는 문제 (Lost in the Middle, 2023)
  • 2025년 중반 토비 뤼트케(Shopify), 안드레이 카파시 등이 용어를 확산

Part 02 · 장단점

컨텍스트 엔지니어링

장점

  • 최신·사내 지식을 모델에 주입
  • 근거 문서 제공으로 환각 감소
  • 사용자별 메모리로 개인화
  • 모델을 바꿔도 파이프라인 재사용

단점

  • 검색 품질이 나쁘면 결과도 나쁨
  • 토큰 비용·응답 지연 증가
  • 정보가 많을수록 주의가 분산됨
  • 조립 파이프라인이 복잡해짐

Part 02 · 예시

매 요청마다 컨텍스트를 조립하기

def build_context(query, user):
    docs    = retriever.search(query, k=5)      # RAG: 관련 문서
    memory  = memory_store.recall(user.id)      # 장기 기억
    history = chat_log.last(user.id, n=10)      # 최근 대화

    return [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "system", "content": f"사용자 정보: {memory}"},
        {"role": "system", "content": format_docs(docs)},
        *history,
        {"role": "user", "content": query},
    ]

프롬프트는 한 줄, 컨텍스트는 시스템 — 무엇을 넣고 무엇을 뺄지가 핵심

Part 03 · 등장 배경

하네스 엔지니어링

도구·실행 환경으로 모델을 감싸기

  • Function Calling (2023) 이후 모델이 직접 도구를 호출하기 시작
  • Claude Code·Codex CLI 같은 코딩 에이전트가 파일 수정·테스트 실행까지 수행
  • 같은 모델이라도 감싸는 환경(하네스)에 따라 결과가 크게 달라짐
  • 에이전트 성능 = 모델 + 하네스 (도구 · 권한 · 샌드박스 · 훅 · 스킬)

Part 03 · 장단점

하네스 엔지니어링

장점

  • 실제 행동 가능 (파일·터미널·브라우저)
  • 권한·샌드박스로 안전하게 통제
  • 도구·스킬 추가로 능력 확장
  • 모델을 바꿔도 하네스는 재사용

단점

  • 설계·유지보수 비용이 큼
  • 도구가 많으면 잘못 고르기 쉬움
  • 프롬프트 인젝션·과도한 권한 위험
  • 하네스마다 동작이 달라 디버깅 어려움

Part 03 · 예시

Claude Code 하네스 설정 (.claude/settings.json)

{

무엇을 허용/금지할지 + 행동 후 자동으로 무엇을 실행할지 = 하네스 설계

Part 04 · 등장 배경

루프 엔지니어링

관찰 → 행동 → 검증을 반복하는 에이전트

  • ReAct (2022) — 추론(Reason)과 행동(Act)을 번갈아 반복하는 패턴
  • AutoGPT (2023) 열풍 → 무한 루프·비용 폭주 문제가 드러남
  • Ralph 루프 (2025) — 같은 프롬프트를 계속 다시 실행하는 단순 루프가 의외로 강력
  • 핵심은 루프 자체보다 종료 조건 · 검증기 · 예산 설계

Part 04 · 장단점

루프 엔지니어링

장점

  • 한 번에 못 푸는 긴 작업 해결
  • 테스트·린터 피드백으로 스스로 수정
  • 사람 개입 없이 자율 실행
  • 구조가 단순해 구현이 쉬움

단점

  • 비용·시간이 폭주할 수 있음
  • 같은 실수를 반복하며 갇힘
  • “완료”를 판단하는 기준 설계가 어려움
  • 작은 오류가 단계마다 누적

Part 04 · 예시

예산 + 검증기가 있는 에이전트 루프

MAX_STEPS = 20

for step in range(MAX_STEPS):              # 1. 예산 (종료 조건)
    action = llm.decide(goal, history)     # 2. 다음 행동 결정
    result = tools.run(action)             # 3. 행동 실행
    history.append((action, result))       # 4. 관찰 기록

    if verifier.passed(result):            # 5. 검증 통과 → 종료
        break
else:
    escalate_to_human(history)             # 예산 초과 → 사람에게

“언제 멈출지”를 모델이 아니라 코드가 정한다

Part 05 · 등장 배경

그래프 엔지니어링

여러 단계·에이전트를 워크플로로 연결

  • 하나의 루프로는 조사 → 작성 → 검토 같은 복잡한 업무를 안정적으로 처리하기 어려움
  • 작업을 노드(LLM·도구·에이전트)와 엣지(조건 분기)로 쪼갠 그래프로 설계
  • LangGraph (2024), CrewAI·AutoGen 등 멀티에이전트 프레임워크 등장
  • Anthropic “Building effective agents” (2024.12) — 체이닝·라우팅·병렬화·오케스트레이터 패턴 정리

Part 05 · 장단점

그래프 엔지니어링

장점

  • 단계별로 관찰·디버깅 가능
  • 독립된 단계는 병렬 실행
  • 노드마다 다른 모델·프롬프트 최적화
  • 체크포인트·재시도·사람 승인 삽입

단점

  • 설계가 복잡해지고 과설계 위험
  • 노드 사이에서 정보가 손실됨
  • 정해진 경로 밖의 상황에 약함
  • 특정 프레임워크에 종속

Part 05 · 예시

LangGraph로 조사 → 작성 → 검토 그래프

from langgraph.graph import StateGraph, END

g = StateGraph(State)
g.add_node("research", research_agent)
g.add_node("write",    writer_agent)
g.add_node("review",   reviewer_agent)

g.set_entry_point("research")
g.add_edge("research", "write")
g.add_edge("write", "review")
g.add_conditional_edges(                      # 검토 결과에 따라 분기
    "review", lambda s: "write" if s["needs_fix"] else END)

app = g.compile()

루프는 그래프의 한 노드가 되고, 그래프는 루프들의 지도가 된다

Bonus 06 · 장단점

gstack

장점

  • 역할별 관점으로 다각도 검토
  • 개발 전 과정을 슬래시 커맨드로 표준화
  • 브라우저 QA 내장 (/browse, /qa)
  • 안전장치 (/careful, /freeze, /guard)

단점

  • 작성자 취향이 강해 팀 방식과 충돌 가능
  • 커맨드가 50개 이상 — 학습 곡선
  • 리뷰 단계가 많아 토큰·시간 비용 증가
  • 업데이트가 잦아 구성이 자주 바뀜

Bonus 06 · 예시

설치 & 기능 하나를 만드는 흐름

# 설치 (Claude Code)
git clone --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack

Bonus 07 · 등장 배경

Lauren Tan의 에이전트 워크플로

  • 에이전트가 사람이 검증할 수 있는 속도보다 빠르게 코드를 생성 → “이게 정말 동작하나?”
  • Lauren Tan (Poteto)이 시니어 엔지니어의 습관을 에이전트가 반복할 수 있는 워크플로로 패키징

  • Cursor 플러그인으로 시작 (MIT) · Claude Code·Codex용 커뮤니티 포트 존재

Bonus 07 · 장단점

pstack

장점

  • 검증 중심이라 결과를 신뢰하기 쉬움
  • 여러 모델이 diff 교차 검증
  • 작업에 맞는 흐름 자동 선택
  • 낯선 코드베이스 빠르게 파악

단점

  • 추론 비용·시간이 큼 (약 2배)
  • 작은 UI 수정 등에는 과함
  • Claude Code 등은 비공식 포트
  • 모델이 발전하면 불필요해질 수도
