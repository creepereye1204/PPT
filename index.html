Part 01 · 등장 배경

프롬프트 엔지니어링

모델에게 무엇을, 어떻게 요청할까

  • GPT-3 (2020) — 몇 개의 예시만 보여줘도 새 작업을 수행하는 few-shot 학습 발견
  • 모델 가중치를 바꾸지 않고 입력 텍스트만으로 동작을 제어할 수 있게 됨
  • Chain-of-Thought (2022) — 추론 과정을 쓰게 하면 수학·논리 문제 정확도가 크게 상승
  • ChatGPT (2022.11) 이후 누구나 쓰는 기술로 대중화 — “프롬프트 엔지니어” 직군 등장

Part 01 · 핵심 개념

프롬프트 엔지니어링의 도구 상자

Zero-shot

예시 없이 지시만으로 수행 — 가장 단순한 출발점

Few-shot

입력→출력 예시 몇 개로 원하는 패턴·형식을 전달

Chain-of-Thought

답하기 전에 추론 과정을 쓰게 해 복잡한 문제 정확도 향상

역할 부여

전문가 페르소나로 어휘·관점·깊이를 고정

구조화 출력

JSON·XML 태그로 형식을 강제해 코드에서 바로 파싱

Self-Consistency

여러 번 샘플링한 답 중 다수결로 선택 (2022)

Part 01 · 동작 원리

프롬프트가 답이 되기까지

각 블록은 독립적으로 고칠 수 있다 — 프롬프트도 “조립”하는 것

Part 01 · 예시

역할 + 지시 + 예시 + 출력 형식

# 역할
당신은 쇼핑몰 고객 리뷰 분석가입니다.
# 지시
리뷰의 감정을 positive / negative / neutral 로 분류하세요.
# 예시 (few-shot)
리뷰: "배송이 빨라서 좋았어요" → positive
리뷰: "포장이 다 찢어져서 왔네요" → negative
# 출력 형식
리뷰: "{review}"
{"label": "...", "reason": "한 문장"}

역할·지시·예시·형식을 분리하면 결과가 안정적이고 수정하기 쉬워진다

Part 01 · 장단점

프롬프트 엔지니어링

장점

  • 비용이 거의 없고 즉시 실험 가능
  • 파인튜닝·학습 데이터 불필요
  • 개발자가 아니어도 활용 가능
  • 빠른 프로토타이핑에 최적

단점

  • 문구 하나에 결과가 흔들림 (취약성)
  • 모델·버전이 바뀌면 다시 튜닝 필요
  • 모델이 모르는 최신·사내 지식은 못 넣음
  • 결과를 체계적으로 평가하기 어려움

Part 01 · 실전 팁

이렇게 쓰세요

✓ Do

  • “3문장 이내”처럼 측정 가능하게 지시
  • 지시·입력·예시를 태그로 명확히 구분
  • 좋은 예시와 나쁜 예시를 함께 제시
  • 프롬프트도 버전 관리 + 평가셋으로 테스트

✗ Don't

  • “절대·반드시” 남발 (과잉 반응 유발)
  • 한 프롬프트에 작업 여러 개 몰아넣기
  • 모델이 모르는 사실을 묻고 그대로 믿기
  • 한두 번 결과만 보고 “좋아졌다” 판단

Part 02 · 등장 배경

컨텍스트 엔지니어링

모델이 보는 정보를 설계하기

  • LLM 앱이 RAG·메모리·도구 결과·대화 기록을 함께 다루게 됨
  • “어떻게 묻느냐”보다 “무엇을 보여주느냐”가 성능을 좌우
  • 컨텍스트 창은 커졌지만 길수록 중간 정보를 놓치는 문제 (Lost in the Middle, 2023)
  • 2025년 중반 토비 뤼트케(Shopify), 안드레이 카파시 등이 용어를 확산

Part 02 · 핵심 개념

컨텍스트 엔지니어링의 도구 상자

RAG

질문과 관련된 문서를 검색해 컨텍스트에 주입

메모리

대화를 넘어 사용자·프로젝트 정보를 저장하고 회상

압축 (Compaction)

길어진 대화를 요약해 컨텍스트 창을 확보

Just-in-time 로딩

미리 다 넣지 않고 필요할 때 에이전트가 직접 조회

도구 결과 관리

거대한 출력은 잘라내거나 파일로 빼고 참조만 전달

서브에이전트 격리

탐색은 별도 컨텍스트에서, 요약된 결과만 반환

Part 02 · 동작 원리

컨텍스트 창은 한정된 예산이다

넣을수록 좋은 게 아니라, “최소한의 고신호 토큰”을 고르는 문제

Part 02 · 예시

매 요청마다 컨텍스트를 조립하기

def build_context(query, user):
    docs    = retriever.search(query, k=5)      # RAG: 관련 문서
    memory  = memory_store.recall(user.id)      # 장기 기억
    history = chat_log.last(user.id, n=10)      # 최근 대화

    if count_tokens(history) > 8_000:           # 너무 길면 압축
        history = [summarize(history)]

    return [
        {"role": "system", "content": SYSTEM_PROMPT},
        {"role": "system", "content": f"사용자 정보: {memory}"},
        {"role": "system", "content": format_docs(docs)},
        *history,
        {"role": "user", "content": query},
    ]

프롬프트는 한 줄, 컨텍스트는 시스템 — 무엇을 넣고 무엇을 뺄지가 핵심

Part 02 · 장단점

컨텍스트 엔지니어링

장점

  • 최신·사내 지식을 모델에 주입
  • 근거 문서 제공으로 환각 감소
  • 사용자별 메모리로 개인화
  • 모델을 바꿔도 파이프라인 재사용

단점

  • 검색 품질이 나쁘면 결과도 나쁨
  • 토큰 비용·응답 지연 증가
  • 정보가 많을수록 주의가 분산됨
  • 조립 파이프라인이 복잡해짐

Part 02 · 실전 팁

이렇게 쓰세요

✓ Do

  • 중요한 지시는 앞이나 끝에 배치
  • 문서에 출처를 붙여 인용 가능하게
  • 오래된 기록은 요약해서 유지
  • CLAUDE.md 같은 프로젝트 메모 파일 활용

✗ Don't

  • “혹시 몰라서” 전부 넣기
  • 검색 품질 평가 없이 운영
  • 서로 충돌하는 지시를 방치
  • 도구 출력 수천 줄을 그대로 주입

Part 03 · 등장 배경

하네스 엔지니어링

도구·실행 환경으로 모델을 감싸기

  • Function Calling (2023) 이후 모델이 직접 도구를 호출하기 시작
  • MCP (2024.11) — 도구·데이터 연결을 위한 표준 프로토콜 등장
  • Claude Code·Codex CLI 같은 코딩 에이전트가 파일 수정·테스트 실행까지 수행
  • 같은 모델이라도 감싸는 환경(하네스)에 따라 결과가 크게 달라짐 → 에이전트 = 모델 + 하네스

Part 03 · 핵심 개념

하네스 엔지니어링의 도구 상자

도구 (Tools)

모델이 호출하는 함수 — 이름·설명·스키마가 곧 모델의 UI

MCP

외부 도구·데이터를 연결하는 표준 프로토콜

권한 (Permissions)

허용 / 거부 / 확인 규칙으로 행동 범위를 제한

샌드박스

파일시스템·네트워크를 격리해 사고 반경을 제한

훅 (Hooks)

도구 실행 전후 자동 스크립트 — 린트·테스트·차단

스킬 (Skills)

필요할 때만 불러오는 절차·지식 묶음 (SKILL.md)

Part 03 · 동작 원리

모든 행동은 게이트를 지난다

“하지 마”라고 부탁하지 말고, 하네스가 막게 한다

Part 03 · 예시

Claude Code 하네스 설정 (.claude/settings.json)

{
  "permissions": {
    "allow": ["Read", "Edit", "Bash(npm test:*)"],

무엇을 허용/금지할지 + 행동 후 자동으로 무엇을 실행할지 = 하네스 설계

Part 03 · 장단점

하네스 엔지니어링

장점

  • 실제 행동 가능 (파일·터미널·브라우저)
  • 권한·샌드박스로 안전하게 통제
  • 도구·스킬 추가로 능력 확장
  • 모델을 바꿔도 하네스는 재사용

단점

  • 설계·유지보수 비용이 큼
  • 도구가 많으면 잘못 고르기 쉬움
  • 프롬프트 인젝션·과도한 권한 위험
  • 하네스마다 동작이 달라 디버깅 어려움

Part 03 · 실전 팁

이렇게 쓰세요

✓ Do

  • 도구 설명은 신입에게 설명하듯 명확히
  • 도구는 적게, 기능이 겹치지 않게
  • 위험한 작업엔 사람 확인 단계
  • 린트·테스트 같은 검증은 훅으로 강제

✗ Don't

  • 프롬프트로 “rm 하지 마” 부탁하기
  • 비밀키를 에이전트가 읽을 수 있는 곳에
  • 웹·문서 내용을 지시처럼 신뢰
  • 도구 결과를 원문 그대로 전부 반환

루프 엔지니어링

관찰 → 행동 → 검증을 반복하는 에이전트

  • Ralph 루프 (2025) — 같은 프롬프트를 계속 다시 실행하는 단순 루프가 의외로 강력
  • 핵심은 루프 자체보다 종료 조건 · 검증기 · 예산 설계

Part 04 · 핵심 개념

루프 엔지니어링의 도구 상자

ReAct

생각 → 행동 → 관찰을 번갈아 반복하는 기본 패턴

검증기 (Verifier)

테스트·타입체크·린터 등 객관적인 통과 기준

예산 (Budget)

최대 스텝·토큰·시간·비용의 상한

자기 반성 (Reflexion)

실패 원인을 글로 남기고 다음 시도에 반영 (2023)

상태 저장

진행 상황을 파일(TODO·노트)로 남겨 언제든 재시작

에스컬레이션

막히거나 위험할 때 사람에게 넘기는 지점

Part 04 · 동작 원리

검증을 통과할 때까지 돈다

“언제 멈출지”를 모델이 아니라 검증기와 예산이 정한다

Part 04 · 예시

예산 + 검증기가 있는 에이전트 루프

MAX_STEPS = 20

for step in range(MAX_STEPS):              # 1. 예산 (종료 조건)
    action = llm.decide(goal, history)     # 2. 다음 행동 결정
    result = tools.run(action)             # 3. 행동 실행
    history.append((action, result))       # 4. 관찰 기록

    if verifier.passed(result):            # 5. 검증 통과 → 종료
        break
else:
    escalate_to_human(history)             # 예산 초과 → 사람에게

Python의 for-else: break 없이 끝나면(= 예산 소진) else가 실행된다

Part 04 · 장단점

루프 엔지니어링

장점

  • 한 번에 못 푸는 긴 작업 해결
  • 테스트·린터 피드백으로 스스로 수정
  • 사람 개입 없이 자율 실행
  • 구조가 단순해 구현이 쉬움

단점

  • 비용·시간이 폭주할 수 있음
  • 같은 실수를 반복하며 갇힘
  • “완료”를 판단하는 기준 설계가 어려움
  • 작은 오류가 단계마다 누적

Part 04 · 실전 팁

이렇게 쓰세요

✓ Do

  • 시작 전에 “완료”를 테스트로 정의
  • 매 반복의 진행 상황을 파일에 기록
  • 같은 오류 N회 반복 시 전략 변경
  • 스텝·비용 상한을 반드시 설정

✗ Don't

  • 모델이 “다 했어요” 하면 완료 처리
  • 종료 조건 없는 무한 루프
  • 실패 로그를 버리고 다시 시작
  • 한 루프에 여러 목표 섞기

그래프 엔지니어링

여러 단계·에이전트를 워크플로로 연결

  • 하나의 루프로는 조사 → 작성 → 검토 같은 복잡한 업무를 안정적으로 처리하기 어려움
  • 작업을 노드(LLM·도구·에이전트)와 엣지(조건 분기)로 쪼갠 그래프로 설계
  • LangGraph (2024), CrewAI·AutoGen 등 멀티에이전트 프레임워크 등장
  • Anthropic “Building effective agents” (2024.12) — 워크플로 패턴을 체계적으로 정리

Part 05 · 핵심 개념

그래프 엔지니어링의 도구 상자

프롬프트 체이닝

병렬화

오케스트레이터-워커

중앙 LLM이 작업을 쪼개 워커에게 위임

평가자-최적화

생성 ↔ 평가를 반복하며 결과를 개선

체크포인트 · HITL

from langgraph.graph import StateGraph, END

g = StateGraph(State)
g.add_node("research", research_agent)
g.add_node("write",    writer_agent)
g.add_node("review",   reviewer_agent)

g.set_entry_point("research")
g.add_edge("research", "write")
g.add_edge("write", "review")
g.add_conditional_edges(                      # 검토 결과에 따라 분기
    "review", lambda s: "write" if s["needs_fix"] else END)

app = g.compile()

앞 슬라이드의 애니메이션이 정확히 이 코드의 실행 흐름

Bonus 07 · 등장 배경

pstack

Lauren Tan의 에이전트 워크플로

  • 에이전트가 사람이 검증할 수 있는 속도보다 빠르게 코드를 생성 → “이게 정말 동작하나?”
  • Lauren Tan (Poteto)이 시니어 엔지니어의 습관을 에이전트가 반복할 수 있는 워크플로로 패키징
  • 핵심 원칙은 검증(verification) — 이해 → 설계 → 검증 → 정리
  • Cursor 플러그인으로 시작 (MIT) · Claude Code·Codex용 커뮤니티 포트 존재

Bonus 07 · 핵심 개념

pstack의 도구 상자

/poteto-mode

진입점 — 작업에 맞는 플레이북과 스킬을 자동 선택

/how · /why

런타임 동작 원리와 코드의 역사적 이유를 파악

/architect

구현 전에 타입과 인터페이스부터 설계

실패하는 테스트를 먼저 작성하고 통과시키기

/interrogate

여러 모델이 diff를 공격적으로 교차 검증

/arena · /swarm

경쟁 시도 중 최선 선택 · 작업을 여러 에이전트로 분할

신뢰도를 쌓아 올리는 4단계

코드를 “빨리” 만드는 게 아니라 “믿을 수 있게” 만드는 데 비용을 쓴다

Bonus 07 · 예시

설치 & 프로덕션 버그를 고치는 흐름

# 설치 (Cursor)
/add-plugin pstack
/setup-pstack    # 모델 라우팅 설정

# 작업에 맞는 플레이북·스킬 자동 선택
/poteto-mode 결제 실패 버그 고쳐줘

/how            # 런타임에서 실제로 어떻게 동작하는지

Bonus 07 · 장단점

pstack

장점

  • 검증 중심이라 결과를 신뢰하기 쉬움
  • 여러 모델이 diff 교차 검증
  • 작업에 맞는 흐름 자동 선택
